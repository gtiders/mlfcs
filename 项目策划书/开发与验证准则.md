# 开发与验证准则

## 1. 公共 API

用户可调用的函数、方法和类必须在定义处提供完整签名、类型、默认值、单位、返回值和异常条件。不得要求用户连续跳转多个包装函数才能理解参数含义。

参数名称应表达物理语义。结构、超胞、截断、温度、统计方式和输出格式不能依赖隐式全局状态。

## 2. 数值行为

修改代码前先保存当前可回滚状态。除非明确批准，不改变已有默认值、索引顺序、随机种子语义、单位或输出物理含义。

任何容差都要说明它判断的数学对象、单位、默认值来源和对结果的影响。诊断性判断不得悄悄变成终止条件。

## 3. 测试与 examples

单元测试验证一个函数或一个不变量；接口测试验证公开工作流；案例验证完整计算和后处理；第三方结果只作为可追溯参考，不作为无法解释的字节级哈希门槛。

每个完整案例至少应说明输入结构来源、reference supercell、拟合或差分方法、截断、温度、输出格式和复现命令。绘图脚本、拟合脚本、分析脚本应分别存在，不使用一个无法解释的总控脚本隐藏步骤。

## 4. 文档格式

所有 Markdown 数学公式使用美元符号：行内公式用 `$...$`，独立公式用 `$$...$$`。中文策划书、实现说明和案例说明优先使用中文；代码中的 API 名称、文件名和外部软件名称保持原样。

## 5. 变更验收

提交前至少执行语法检查、相关单元测试、一个有限差分或拟合案例、一个格式写出案例和 `git diff --check`。报告必须区分“代码测试通过”“案例实际运行”和“第三方程序读取通过”。
